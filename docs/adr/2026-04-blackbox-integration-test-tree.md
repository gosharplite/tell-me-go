# ADR-017: Black-Box Integration Test Tree at `tests/`

## Status
Accepted

## Context

`tell-me-go` follows a Hexagonal Architecture in which behavior lives under
`internal/...`. Tests for that behavior currently live in two distinct locations:

1. **In-package (white-box) tests** — `*_test.go` files that share the package
   declaration of the code they exercise (e.g., `package session` in
   `internal/agent/session/`). These have full access to unexported symbols and remain
   the default for unit tests.
2. **Out-of-package (black-box) tests** — files under `tests/integration/...` and
   `tests/e2e/...` that declare a separate `_test` package (e.g., `package session_test`)
   and import the code under test through its exported API only. These exercise
   cross-package collaboration and full-binary scenarios.

This split arose organically as the `internal/agent/...` packages grew and required
multi-component scenarios that no single in-package test could express. The convention
has never been formally recorded.

The absence of a written rule recently produced a concrete failure mode: a refactoring
proposal generated by a dead-code analyzer scoped to `./internal` recommended unexporting
several types in `internal/agent/session/` as "unused within the package". The symbols
were in fact load-bearing public API consumed by `tests/integration/agent/session/`, and
the refactor was halted just before damage was committed. The same blind spot recurred in
a subsequent session, confirming that this is a systemic risk requiring a permanent
architectural record rather than a one-off correction.

## Decision

We codify the existing two-tier test layout as a binding architectural rule.

1. **Locations are fixed.**
   - Black-box integration tests for `internal/...` packages live under
     `tests/integration/...`, mirroring the source path of the package under test.
   - Full-binary, end-to-end scenarios live under `tests/e2e/`.
   - White-box unit tests live in `*_test.go` files inside the package they test, with
     the same package declaration.

2. **The choice between locations is mechanical.**
   *Does the test require access to unexported symbols?*
   - **Yes** → place it in-package (white-box).
   - **No** → place it under `tests/...` (black-box).

   This rule keeps the public surface honest: a contributor who needs to add a
   black-box test must consciously decide whether to export the symbols it depends on.

3. **`tests/` defines the public contract.**
   Any symbol referenced from `tests/` is part of its package's de-facto public API and
   is subject to the same compatibility considerations as a symbol referenced from
   `cmd/` or from another `internal/` package. Unexporting, renaming, or removing such a
   symbol is a breaking change that must refactor the `tests/` callers in the same
   commit.

4. **Static-analysis tools must be scoped to the whole module.**
   Dead-code analyzers, dependency graphs, and refactoring planners used to justify
   architectural changes MUST be invoked with module-wide scope (`./...`). Scoping them
   to a subset such as `./internal` will report every symbol consumed from `tests/` as
   unused and will produce unsound recommendations. This is a process rule that follows
   directly from the architectural choice above.

5. **Discoverability is mandatory.**
   The `tests/` tree carries a `README.md` that names this convention, lists the
   subdirectories, and instructs contributors to run `grep -rn "<SymbolName>" tests/`
   before unexporting any symbol.

## Consequences

### Positive
- Tests exercise `internal/...` packages exactly as production callers do, so accidental
  breakage of the public surface is caught by the test suite rather than at the call site.
- Adding a black-box test forces an explicit export decision, encouraging narrow and
  intentional public APIs.
- Integration and end-to-end tests are physically separated from unit tests, which
  simplifies targeted CI runs and keeps unit-test feedback loops fast.
- Refactors that touch only unexported internals can proceed without modifying any file
  under `tests/`, giving a clean signal that the change is non-breaking.

### Negative
- Tooling that scans only `./internal` will report false-positive "unused export"
  findings for every symbol consumed from `tests/`. Mitigated by the module-wide scoping
  rule in the Decision section.
- Some helpers that would otherwise remain unexported must be exported solely to support
  black-box tests, slightly enlarging the public surface of a few packages.
- Splitting tests across two locations imposes a small contributor-education cost,
  mitigated by the `tests/README.md` introduced alongside this ADR.
